1. What it does and does not do Current

Your app's screens and assets → Base App → one Expo project that runs, debugs and bundles on Android, iOS and web.

For a game that is only a Phaser scene there is a second, optional path: the same scene → capacitor/ → an Android/iOS app with no React Native. You pick one path per app.

Base App does not contain game rules, a backend server, user accounts or any vendor API key.

Does

Gives a new app the parts that kept recurring across Bounce Fidget, Pinbolita, Tessera, Bingepick and proyecto-comun, already wired together: navigation, translations in 6 languages, saved settings, theme, menus, a game loop, Phaser, audio, haptics, tilt, an API/LLM client, icon generation, an Android release-signing plugin (your keys stay outside the repo, see Private machinery), a rename script, on-screen touch buttons for Phaser scenes, and an optional Capacitor shell.

Does not

Decide gameplay, host anything, or hold secrets. The demo screens under src/app/demos/ are examples to delete, not features. It never calls a model vendor directly; that is your backend's job.

Public handoff

What ships to users: the JS bundle (including every EXPO_PUBLIC_* value, which is readable by anyone), the assets, and the requests the app sends.

Private machinery

What never ships: credentials/ (upload keystore and passwords, gitignored), .env.local, and on your backend the vendor keys and prompts. On the device, settings and the client id stay in local storage.

3. Walkthrough: one frame, one launch, one refusal Current A, B · Verify C

Three scenarios, each taking a different path. Every number in scenario A and B was produced by running Base App's own modules on these inputs, not worked out by hand. The inputs are illustrative; the outputs are what the code returns for them. Separately, the on-screen result of A (the ball rolling, bouncing and the counter rising) and of B (Spanish surviving a restart) was observed on the Android emulator.

A. One game-loop frame: a tilt sample becomes a bounce, a sound and a buzz

Setup: the /demos/game-loop screen on a 120 Hz phone. The ball (radius 22) is 23 px from the left edge, moving left at 3 px/frame. The screen area is 360 × 560.

Every block in this trace is a semantic display excerpt: values computed by the real functions, not a stored or wire shape.

  1. A1expo-sensors → tiltSensor.ts:onSample

    The accelerometer delivers a sample (every 16 ms, tiltSensor.ts:54). deviceToScreen flips X only, because device Y grows up while screen Y grows down (tilt.ts:39).

    sample (g) {x: 0.2, y: 0.1}  →  screen {x: -0.2, y: 0.1}
  2. A2tiltSensor.ts:43

    Smoothed toward the sample (weight 0.35), then the 0.03 g dead zone is subtracted so input starts from zero at its edge instead of jumping. The result is written to the module-level tilt.gravity.

    smoothed {x: -0.07, y: 0.035}  →  tilt.gravity {x: -0.0432, y: 0.0216}
  3. A3GameLoopView → frameScale.ts:12

    RNGE ticks on requestAnimationFrame. At 120 Hz the delta is 8.33 ms, so dtf = 0.5. Every force is multiplied by it; that is why the ball moves at the same speed on 60 Hz and 120 Hz screens.

    deltaMs 8.33 → dtf 0.5
  4. A4demos/game-loop.tsx:63 → bounce.ts:22 stepBall

    The system scales tilt by TILT_ACCEL 1.3, integrates with friction 0.995 and bounciness 0.7, and hits the left wall: position clamps to the radius, the impact speed is taken before reflection, then velocity reverses at 70%.

    gravity in  {x: -0.0561, y: 0.0281}
ball in     {x: 23, vx: -3,     vy: 0}
ball out    {x: 22, vx: 2.1143, vy: 0.014}
impact      3.0205
  5. A5demos/game-loop.tsx:66–68 → SoundBank.ts:55, haptics.ts:15

    The impact is above the 1.5 feedback floor, so three things happen. The sound bank plays a non-repeating bounce variant at gain impactGain(3.02, 14, 0.25). It skips playback entirely when Sound is off (SoundBank.ts:57). Haptics fires a light impact (under 5) unless Vibration is off or the platform is web (haptics.ts:8). The bounce counter increments.

    gain 0.25 (the floor; 3.02 / 14 = 0.22)   haptic "light"   bounces + 1

    Verify The counter was observed. The sound and the buzz were not: nobody listened, and emulators have no vibration motor.

  6. A6RNGE DefaultRenderer → BallView

    RNGE re-renders the mutated entity. BallView starts with 'use no memo'. Without it the React Compiler memoises the component and the ball freezes on its first frame. This was observed on Android and web: 2 renders instead of thousands.

    The splash stays up while the settings store loads from storage, so the first frame never flashes the wrong language or theme.

    Only state reaches mergeSettings. Each field is validated on its own: a bad value falls back to that field's default, numbers clamp, unknown keys are dropped. Below is what the real function returns for a corrupted record.

C. A boundary case: the backend refuses with 429 Verify

This path shows a typed refusal rather than a success. Steps C1–C4 are in the code and their pure parts are unit-tested, but the full path has not been observed on a device: the end-to-end attempt on the emulator didn't complete. Requires EXPO_PUBLIC_API_URL.

  1. C1demos/api.tsx → llm/HttpStreamProvider.ts → client.ts streamText

    The screen sends an LLMRequest to /v1/chat on your backend, with headers x-client-id (persisted install id), content-type: application/json and accept: text/plain, text/event-stream, application/json.

    Schema-valid against LLMRequest — the complete request body

    {"messages":[{"role":"user","content":"hola"}],"locale":"es"}
  2. C2your backend

    The backend, not this app, decides the quota. Tessera's relay is the reference: a per-client daily limit that answers 429 with a Retry-After header and/or JSON retryAfterSeconds. The client id is not authentication; the backend must not trust it for anything beyond rate limiting.

  3. C3client.ts errorFor → retry.ts

    429 is not retried (isRetryable(429) is false; the server said when to come back). Network errors and 5xx are retried twice with backoff. The header becomes milliseconds and a RateLimitError is thrown.

    Semantic display excerpt — return values of parseRetryAfter and backoffDelay

    Retry-After "42" → retryAfterMs 42000          backoff for 5xx: 400, 800, 1600 ms (+ up to 50% jitter)
  4. C4demos/api.tsx

    The screen shows the localised message. With no Retry-After it assumes 60 s.

    Translated string api.rateLimited (es) with seconds = 42

    "Demasiadas solicitudes. Inténtalo de nuevo en 42 s."

4. Three mechanisms that make it work Current

One store, read two ways

The game loop, the sensor callback and the audio engine run outside React's render cycle, every frame. They read settings synchronously with useSettings.getState(), while screens subscribe with useSettings(selector). Bounce Fidget kept settings in module variables and wrote to both places; forgetting one write made the slider move while the ball ignored it. One store removes that class of bug.

Illustrative diagram

Settings screen ──set()──► useSettings (zustand, persisted, validated)
                                 │
          React screens ◄── subscribe        frame loop / sensors / audio ◄── getState()

Phaser: one scene, three hosts

Phaser needs a DOM and a canvas, and React Native has neither. So the same scene code runs in up to three places:

Shared

scenes/*.ts + game.ts import only phaser and relative files. They talk to the host only through bridge.ts.

Web host

PhaserView.web.tsx dynamic-imports game.ts and mounts Phaser into the page. Phaser lands in its own chunk (1.66 MB in the expo export output, measured at 81ddd19), not the main bundle.

Native host

npm run phaser:build (also run on postinstall) bundles Phaser + scenes into one HTML string (1,362 KB at 4aa38bf, as the script reports). PhaserView.tsx loads it in a WebView. It works offline.

Capacitor host (optional)

capacitor/src/main.ts calls the same startGame with Vite and no React Native. On native it adds the app glue: Android back exits, backgrounding releases keys and pauses.

Schema-valid against GameEvent in bridge.ts — game → host, sent as a JSON string through postMessage on native

{"type":"bounce","count":11}

Schema-valid against HostCommand — host → game; native wraps it as window.__hostCommand(…)

{"type":"pause"}

The menu system drives the game: any open menu sends pause, and closing sends resume. On pause the scene also calls keys.releaseAll(), so a button held when the menu opened is not still held after it closes.

Input: one latch, two sources, sampled once per tick

On a touch device game.ts mounts the scene's buttons (BOUNCE_BUTTONS: ◀, ▶, JUMP) over the canvas; on a keyboard the arrow keys and Space write to the same latch. Each button holds its key while its finger is down (pointer capture, multi-touch) and stops the touch reaching the canvas. The scene calls keys.sample() at the top of update(), then reads pressed and justPressed. A key stays pressed until every source has let go.

Semantic display excerpt — what the real KeyLatch returns for LEFT after each sample()

TickEventTrue after sample()
1touch downpressed, justPressed
2keyboard down as wellpressed
3touch uppressed (the keyboard still holds it)
4keyboard upjustReleased
5nothingnone
anya tap that starts and ends between two samplesall three
justPressed lasts exactly one tick. That is why the demo's JUMP kicks on every press instead of checking "on the ground": a bouncing ball is grounded for so few frames that a grounded check plus a one-frame press missed almost every tap. A real platformer needs a ground check and a jump buffer of a few frames.

5. Data anatomy: what is public, what stays private Current

In the bundle — public

  • All JS, translations, sounds, images
  • EXPO_PUBLIC_API_URL and any other EXPO_PUBLIC_* value (inlined at build time)
  • The app identity in app.json

On the device — not shared unless sent

  • @<slug>:settings — settings record (B2)
  • @<slug>:client-id — anonymous UUID, created on first HTTP request
  • @<slug>:sound:<slot> — custom sound {uri, name}, file copied to the documents folder

The slug prefix keeps two apps apart on web, where every app you develop shares localhost:8081 storage.

Never in the repo or bundle

  • credentials/ — upload keystore + passwords, read by Gradle at build time only
  • .env.local
  • Vendor API keys and prompts — your backend's

"Not shared" is not "secret": once the client id is sent to your backend it is observable and replayable. What the backend must re-check itself: anything the app sends. A request reaching the backend proves nothing about the sender. The client id is replayable, and the bundle can be read.

6. Developer lifecycle: build, rename, sign, package Current · Verify release signing

This is separate from the runtime above: what you do to make a new app from Base App and ship it.

  1. D1scripts/rename-app.js Current

    npm run rename -- "Laberinto de Bolita" rewrote app.json (used for real on 2026-10-20). Prebuild then carried the ids into both native projects.

    Real output of npm run rename, condensed to one line per id

    slug laberinto-de-bolita · scheme laberintodebolita
android io.github.ivan_i1.laberinto_de_bolita · ios io.github.ivan-i1.laberinto-de-bolita
storage prefix @laberinto-de-bolita · version 0.1.0 · versionCode 1
  2. D2scripts/generate-icons.mjs Current

    One square image in assets/source/icon.png (plus an optional transparent foreground.png) → iOS/Android icon, adaptive foreground/background/monochrome layers, splash, favicon, and the 512 px Play icon. Needs ImageMagick 7.

  3. D3expo prebuild → plugins/withReleaseSigning.js Verify

    On every prebuild the plugin adds a release signing config that reads credentials/keystore.properties at Gradle time. Without it, release builds fall back to the debug key with a warning, and Play rejects those. The patch was confirmed in the generated build.gradle. A signed release build has not been run.

  4. D4npm run check · export:web · export:native Current

    Typecheck + 55 unit tests (11 suites) + lint. All ran green on 4aa38bf on 2026-10-21; the three bundle builds last ran on 81ddd19. These gates only reach the pure logic; rendering, audio, haptics and sensors need a device.

  5. D5capacitor/scripts/prepare-native.mjs Current · Verify release

    Only for the optional Capacitor path. npm run cap:install once, then npm run cap:apk / cap:bundle / cap:ios. The script writes capacitor.config.json from app.json, generates capacitor/android and capacitor/ios (gitignored), makes icons and splash from assets/source/, and patches: immersive full screen, release signing from the same credentials/, versions, orientation, the iOS bundle id and a hidden status bar. Running it twice leaves the patched files byte-identical. Needs JDK 21 (Android Studio's bundled runtime works; the system JDK 17 does not). A debug APK and an iOS simulator build were made; a signed release has not been.

8. Not included Deferred

  • Deferred EAS build config (eas.json). Builds are local (expo run:*, Gradle). EAS can be added later.
  • Deferred Ads, analytics, leaderboards. None of the source apps or plans use them; leaderboards were explicitly deferred to local-only in the Dino-runner plan.
  • Deferred UI / device tests. Only pure logic is unit-tested.
  • Proposed On-device LLM provider. Tessera has a stub interface for one. Base App's LLMProvider would accept it, but none exists.
  • Deferred Multi-scene back navigation in the Capacitor shell. Android back exits the app, which is right for one scene; a title screen would need back to go there first.
  • Deferred Collision beyond screen edges. Maze walls, holes and sub-stepping belong to the app (see laberinto-de-bolita's ADV-REV-V1 §3.4).
